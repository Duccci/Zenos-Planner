## Summary

Comprehensive refactoring and cleanup of Zeno's MCP server implementation addressing both code architecture and user experience. Refactor three monolithic files (948 + 928 + 478 lines) into focused domain-specific modules using handler factory pattern (40% → <5% duplication), while simultaneously improving end-user experience via simplified setup, VSCode resources, and enhanced error handling. Breaking changes acceptable for improved UX and maintainability.

## Context

**Code Quality Issues** (Refactoring):
- Monolithic files: `function-implementations.ts` (948 lines), `src/mcp/tools/*.ts` (928 lines combined), `workflow-logic.ts` (478 lines)
- ~40% code duplication in handler patterns
- Single developer per file (merge conflicts, parallel work blocked)
- Difficult to locate specific functions (948-line searches)

**User Experience Issues** (Cleanup):
- Complex MCP setup process with multiple manual steps
- Missing VSCode-standard features (resources)
- Inconsistent error messages
- No development mode support
- Unused/dead code in codebase

**Analysis Source**: ANALYSIS_MCP_vs_PROMPTS.md § 3 (Monolithic File Analysis)

### Task 4: Refactor Tool Handlers to Use Factory

**File(s)**: `src/mcp/tools/*-tools.ts`

**Status**: DEFERRED - Requires Careful Analysis

**Analysis**: Attempted bulk refactoring using `createSchemaValidatingHandler` factory broke 5+ test files due to:
- Factory's generic output extraction doesn't preserve specialized handler logic (array parsing, JSON extraction)
- Tests expect specific `structuredContent` formats that factory doesn't produce
- Complex handlers have unique error message formatting needs

**Recommendation**: Instead of forced factory pattern, keep current working implementations and:
1. Document why certain tools can't use factory (specialized logic)
2. Consider selective application only to simple handlers (config_get, show_entity)
3. Plan incremental refactoring in separate proposal focusing on understanding tool-specific patterns
4. Accept current code duplication (928 lines) as technical debt for now

**Current Status**: 
- ✅ Original tool handlers restored and working (709/710 tests passing)
- ✅ Handler factory still available for future selective use
- ⏳ Task 4 deferred pending detailed analysis of tool-specific patterns

**Future Approach**:
- Analyze each tool file individually (10 tools)
- Classify by complexity: simple (config, show) vs complex (proposal, analysis, repository)
- Apply factory pattern only to simple tools first
- Document reasoning in each tool file about why factory is/isn't used
